# Versioning policy

droid-mcp follows [Semantic Versioning 2.0.0](https://semver.org/). This page covers what the version numbers promise, which APIs they cover and how that is enforced.

## Version numbers

| Part | Meaning |
|---|---|
| MAJOR | Incompatible API changes. From 1.0 on, this is the only place a breaking change is allowed. |
| MINOR | New, backward-compatible capability: new modules, tools, optional builder methods, or tool parameters with defaults. |
| PATCH | Backward-compatible bug fixes only. |

## What the contract covers

From 1.0 on, none of these change without a major version bump:

- The `McpTool` interface (`name`, `description`, `parameters`, `annotations`, `execute`).
- The shapes of `ToolResult`, `ToolParameter`, `ParameterType` and `ToolAnnotations`.
- `DroidMcp.Builder` method names and defaults.
- **Each tool's wire contract:** its name, its parameter names and its result-map keys. Renaming any of them is a breaking change.
- Module coordinates (`com.github.stixez.droid-mcp:droid-mcp-<name>` on JitPack).
- MCP protocol behavior: `initialize`, `tools/list`, `tools/call`, error codes and the JSON-RPC envelope.

Internals such as `McpProtocolImpl` internals, transport plumbing and parsing helpers are not part of the contract and may change in any release.

## How it is enforced

Two CI checks fail the build on any unreviewed change:

| Check | What it guards | After an intended change |
|---|---|---|
| `apiCheck` | Each library's public JVM API, dumped to `<module>/api/<module>.api` (binary-compatibility-validator format, generated by `tools/abi-dump`) | Run `./gradlew :<module>:apiDump`, review the diff and commit it |
| Tool contract snapshot (`ToolContractTest`) | `droid-mcp-all/api/tool-contract.txt`: every tool's name, annotations and parameters (type, required, items, enum, range) | Run `./gradlew :droid-mcp-all:testDebugUnitTest -PupdateToolContract` and commit the diff |

Result-map keys can't be introspected, so neither check covers them. Reviewers catch those.

## Before 1.0

Semver allows breaking changes in any pre-1.0 release. droid-mcp still avoids them: since 0.4.0 no tool, parameter or result key has been renamed or removed, and cleanup alone is never a reason to rename.

The exception is a bug fix whose correct behavior differs from the broken one. For example, in 0.11.0 `slot_index` holds the SIM slot as documented, and `set_node_text` no longer uses its replacement text as a selector. Each such change is listed in the release notes.

> [!IMPORTANT]
> 0.11.0 is source-compatible with 0.10 but not binary-compatible. Rebuild code that was compiled against 0.10 instead of swapping in the new artifacts.

## Deprecation

From 1.0 on:

1. A symbol marked `@Deprecated` keeps working for at least one full minor release.
2. The deprecation message names the replacement.
3. Removal happens only in the next major version.

Typealiases kept for source compatibility (for example `playback.NotificationListenerHolder`) stay indefinitely.

## Releases

- Releases are published through JitPack from git tags named `vMAJOR.MINOR.PATCH`. Maven Central may follow after 1.0 if there is demand; for consumers it would be a coordinate change, not a migration.
- Release notes are on [GitHub Releases](https://github.com/stixez/droid-mcp/releases), generated from each tag's commit history. `CHANGELOG.md` is a local, gitignored maintainer file and is not published.

## Support window

The latest minor release is supported. Critical security fixes may be backported to the previous minor at the maintainer's discretion. There is no long-term support before 1.0.
